测什么

速度

DiT 每步（ms/step，中位数 / p10 / p90），热端到端，冷端到端，冷编译。

画质

PSNR、SSIM，都和 CPU fp32 参考结果比（同样的 prompt、seed、50 步、同一份初始噪声）。

冷启动的两种口径

A：native 用 weight store（主数字，和 AoT 的预切分文件对称）。B：native 关掉 store。先做 A 和 AoT，B 放在最后。

已确认的规则

项目决定
双 core attention两边都用。native 已经是双 core，不用改代码（编译出的程序里 attention 拆成 lnc0 / lnc1 两个子图）。AoT：Qwen、HunyuanVideo 在 main 上默认就是；LTX-2、Wan 要设 NEURON_RT_VIRTUAL_CORE_SIZE=2，并核对 DiT 确实编成了双 core 版本。
AoT 用哪份代码最新的 main（含 bf16 修复），在单独的 worktree /home/ubuntu/aot-main 里跑，不动当前分支。修复前测的 AoT 数字全部不复用。
dtype两边尽量 bf16。native 的 Wan umT5、Wan VAE、Qwen VAE 在主测量（设备、CPU 参考、报告、口径 B）里都维持 fp32；之后的第 3 批再把它们改成 bf16 重测，umT5 要先过 F13 的精度检查。
冷启动定义清空 page cache；全新进程、全新工作目录；跑满 50 步；文本编码器、DiT、VAE 的权重都在计时内从磁盘读；不复用任何中间结果；编译好的程序可以事先存在。
LTX-2 Gemma从代码上修（F12），在 LTX-2 native 测量之前完成。
CPU 参考全部 50 步，共 7 份（Qwen、LTX-2、HunyuanVideo 各两份，Wan 一份），先做 Qwen 和 LTX-2。
磁盘方案 A：删除修复前的旧 AoT 编译目录。
测量工具放在仓库外的测试目录，不改产品代码。
F11这次不做。

执行顺序和并行

横轴是从现在开始的小时数（估算）。同一条泳道里的任务必须一个接一个做；不同泳道之间，只有绿色的轻任务可以和设备任务同时进行。

不能并行设备上的测量

每个测量都用 TP4，占满 4 个 core，两个模型不能同时上设备。

不能并行CPU 参考和设备测量

CPU 参考会占满 12 个 vCPU、60–82 GB 内存和磁盘带宽，还会挤掉 page cache，热启动、冷启动和编译的计时都会被干扰。

不能并行CPU 参考之间

每份要 60–82 GB 内存，整机 124.8 GiB，同时跑两份会内存不够；CPU 也被同一组核心分走，并不会更快。

可以并行轻任务和设备测量

F12、bf16 改动、参考脚本和画质工具的准备、文档。单元测试会打开 /dev/neuron0，只在设备空闲的空档跑。

顺序说明：第 2 批之后直接跑 CPU 参考和报告，主测量的结果（包括画质）约 22 小时后出来。口径 B 放在第 3 批之前，因为 B 要和口径 A 用同样的 dtype（fp32 umT5）比较。第 3 批的代码可以在设备测量期间提前写好，到时只剩设备上的验证和重测。

各批次的内容

  1. 第 1 批：准备 + Qwen-Image、LTX-2 的 AoT

    运行中约 2.5 h · 设备
    • 建 aot-main worktree，确认 bf16 修复相关的 commit 都在；按方案 A 清理旧的 AoT 编译目录；准备测试脚本和计时 probe。
    • 每个模型：冷编译 → 冷端到端 → 预热一次 → 3 次热端到端 → 一次画质运行（输出无损文件，并保存初始噪声）。

  2. F12：修复 LTX-2 Gemma 加载问题

    运行中约 1.5 h · CPU
    • 加载器改成按要加载的 key 选择 index，加单元测试，再在真实 snapshot 上核对 Gemma 的 626 个 key 都能找到。

  3. 第 2 批：LTX-2 native、HunyuanVideo / Wan AoT

    待开始约 5 h · 设备
    • Qwen native 核对 hash + 画质运行 → LTX-2 native 完整测量（口径 A）→ HunyuanVideo AoT → Wan AoT（双 core、设备上的 bf16 VAE）→ HunyuanVideo / Wan native 核对 hash + 画质运行。

  4. CPU 参考

    待开始约 14 h · CPU
    • 7 份、全部 50 步，按 Qwen ×2 → LTX-2 ×2 → Wan ×1 → HunyuanVideo ×2 的顺序串行。每份跑之前，先核对它的初始噪声和设备运行保存的一致。

  5. 画质指标和报告

    待开始约 0.5 h · CPU
    • 每帧 PSNR（平均和最差）、SSIM，加上潜变量的 rel-L2 和余弦相似度，汇成 4×2 总表，每个数字注明 commit、日期和日志路径。

  6. 口径 B

    待开始约 0.75 h · 设备
    • Wan 和 LTX-2 的 native 冷启动，关掉 weight store，从原始 checkpoint 读。放在第 3 批之前，和口径 A 用同样的 dtype。

  7. 第 3 批：bf16 改动并重测（含 umT5）

    最后做约 4.75 h · 设备
    • Qwen 和 Wan 的 VAE 改成 bf16，验证精度（≥ 50 dB）。
    • Wan 的 umT5 改成 bf16 前先过 F13 的精度检查：逐个 prompt 和 fp32 比（含空的 negative prompt，余弦 ≥ 0.995），再跑一次 50 步端到端；不通过就保留 fp32。
    • 然后重测 Qwen 和 Wan 的 native，并把这部分结果作为补充写进报告。

第 1 批要点：

  • 两个模型都在最新 main（540e5f0）上跑，每个进程都确认加载的是 aot-main 的代码；HLO 里 DiT 的 all-reduce 全是 bf16。
  • Qwen-Image：bf16 修复让 AoT 每步从 418.2 ms 降到 360.6 ms（−13.8%），和 native 的 359.0 ms 基本持平。热端到端 AoT 73.7 s，native 82.3 s；冷端到端两边接近（AoT 515.6 s，native 502.0 s）；编译 native 快得多（187.0 s 对 1209.9 s）。
  • LTX-2：双 core 已确认（DiT 编成 MODULE_e1043f48，288 个 attention 调用全部 grid 2）。每步 400.1 ms（10-20 修复前 419.2 ms）。冷端到端 778.1 s 中 88% 是读权重：主机上的 Gemma 等组件 373.8 s，DiT 309.7 s。
  • LTX-2 的画面只部分符合 prompt：雪林正确，但狐狸认不出来。guidance 1 没有 CFG，以前 20 步的结果也是这样；等 CPU 参考出来再判断。

第 2a 批要点：

  • Qwen-Image native 核对通过：在当前代码上重跑一次，输出 PNG 和潜变量都和 10-25 逐位一致，所以 10-25 的 native 数字可以直接用（这次每步 358.6 ms，10-25 是 359.0 ms）。初始噪声已保存，供 CPU 参考使用。
  • HunyuanVideo AoT（最新 main）：双 core 和 bf16 都在 HLO 里确认（60 个 attention 全部 grid 2，124 个 all-reduce 全是 bf16）。每步 801.8 ms，修复前 813.9 ms（−1.5%）。
  • 和 native 比：DiT 每步 AoT 快 0.8%（801.8 对 808.2 ms）；热端到端 native 快（126.7 对 133.0 s）；冷端到端 native 快得多（457.8 对 617.5 s）；编译 native 快得多（274.5 对 4526.7 s，AoT 有 81% 花在编译 VAE 上）。峰值 HBM：AoT 每个 core 15.53 GiB；native 的 rank 0 是 17.95 GiB（VAE 也在这个 core 上），其他三个 core 12.98 GiB。
  • 画面是雪地里奔跑的红狐，符合 prompt。AoT 的初始噪声已保存，并确认能在 CPU 上用 torch 2.9 逐位复现。

决策记录

执行中遇到问题时，按默认建议处理并记录在这里。最新的在最上面。

时间问题采用的做法原因
10-26main 的 HunyuanVideo AoT 不保存初始噪声，没法核对 CPU 参考用的是不是同一份噪声在测试 probe 里加了一个可选的保存功能，只在画质运行时打开不改仓库代码；这样 CPU 参考能从完全相同的噪声出发，也能比较潜变量。已确认 CPU 上用 torch 2.9 能逐位复现这份噪声。
10-26main 的 HunyuanVideo AoT 各阶段不转发 --revision接受，不改 main本机 HF cache 里只有一个 snapshot（e8c2aaa6），只可能加载到这一版。
10-26Qwen native 核对时，热启动运行里多编译了一个小 NEFF（20 s），这次的端到端时间不能当热启动数字继续用 10-25 的 native 数字，不重跑完整测量判定标准是输出逐位一致，已满足；每步时间也一致（358.6 对 359.0 ms）；新 NEFF 和已有的只差调试信息。
10-26Qwen native 核对要在 10-25 的编译目录上跑复制一份再跑，不动原目录保留 10-25 的原始证据不被改写。
10-26F12 复查结果没有发现问题，LTX-2 native 按计划在 2c 跑复查确认：只有一个 index 或没有 index 的目录行为不变；weight store 和加载器选的是同一个 index；选择时只读 index 和文件头，不读权重。
10-26F12 的独立复查还没结束，LTX-2 native 是否等它第 2 批拆成三段，LTX-2 native 放到最后（2c）给复查留出时间；如果复查发现问题，先修好再跑 LTX-2 native。
10-26LTX-2 AoT 的画面里狐狸认不出来保持原 workload（guidance 1），不改参数这是你指定的对比设置；以前 20 步的结果也一样。CPU 参考出来后用 PSNR/SSIM 判断是模型本身还是设备的问题。
10-26最新 main 的 CLI 没有 --backend 参数，第一次编译直接报错改用环境变量 DIFFLET_BACKEND=trainiummain 靠这个变量选后端；只改了测试脚本，没动代码。失败的运行保留在日志里。
10-26Qwen 第一次冷启动运行在监控超时时被中断把那次运行隔离保存，重新跑一次完整的冷启动中断的数据不完整，不能用；之后改成用 systemd 托管长时间运行。
10-26HunyuanVideo 旧 AoT 目录删除后只释放了 16 GB不再删除批准范围外的文件它的权重文件和 ~/.cache/difflet 下的目录是硬链接，那些目录不在批准删除的范围内；清理后可用空间已有 386 GB，够用。
10-26口径 B 放在哪里放在画质报告之后、第 3 批之前B 要和口径 A 用同样的 dtype（fp32 umT5）比较；第 3 批改成 bf16 后再测 B 就不可比了。
10-26F12 的单元测试会打开 /dev/neuron0代码先写，测试只在设备空闲时跑避免干扰正在进行的设备计时。
10-26CPU 参考和设备测量能不能并行不并行，CPU 参考放在设备第 2 批之后CPU 参考占满 CPU、内存、磁盘并挤掉 page cache，会干扰热启动和冷启动的计时。
10-26native 是否需要改代码才能用双 core attention不需要编译出的程序里 attention 已经拆成 lnc0 / lnc1 两个子图，和 AoT 的双 core 版一样。
